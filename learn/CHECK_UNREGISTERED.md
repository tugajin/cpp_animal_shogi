# 未登録68%の原因調査 手順

実験4.5-C で、自己対局局面サンプル20,000件のうち 68.1%（13,613件）がオラクルDB（win/lose/draw.dat）に未登録だった。実験5（オラクル混合学習）の設計は「自己対局局面にオラクルラベルを付けられるか」に依存するので、この理由を先に確定させる。

## 実行

```bash
cd ~/Documents/cpp_animal_shogi/learn
../.venv/bin/python check_unregistered.py
```

出力は `check_unregistered_result.md`。モデルは使わない（torch不要）。オラクルDBの読み込みが主な所要。

## 仮説と、それを判別する仕掛け

| # | 仮説 | 判別方法 |
|---|---|---|
| H1 | ハッシュ/DB の対応自体が壊れている（エンコード不一致など） | 対照A: 平手からのランダム合法プレイアウト局面の登録率。正常ならほぼ100%のはず。低ければこちらが本命 |
| H2 | ランダム初期局面が「実戦では到達できない局面」を大量に含み、DBの収録範囲（到達可能局面）から外れている | 対照B: `generate_random_position()` の近似再現の登録率が自己対局並みに低ければ支持 |
| H3 | 未登録は静的に違法な局面（非手番側への王手放置、両ライオン同時王手、最奥段のひよこ等）に集中している | 本体の層別表: 違法系特徴を持つ局面の登録率が際立って低く、持たない局面が高ければ支持。生成関数の棄却条件は「attacker数>1」だけで、王手放置（attacker=1）は素通りする点が根拠 |
| H4 | DB側がキーを正規化している（手番を揃える等） | 未登録キーについて手番反転キー（key ^ 1）の登録を照合。ヒットが多ければ支持 |
| H5 | 世代やグループ固有の問題（最新世代だけ壊れている等） | グループ別登録率（gen_12〜16 + data）。全グループ同水準なら構造的な話 |

## スクリプトの内容

- **self-test**: ハッシュの decode/encode を平手キー（1248110771415179264）で照合してから始める。盤面の段の対応（index 0..2 が後手陣）は平手 decode の実測で確定させた（推測で書いて初版で実際に間違えたので、必ず self-test の OK を確認すること）
- **本体**: 実験4.5-C と同一サンプル（`data` グループ、seed=123、20,000件）を、手番・王手・トライゾーン・最奥ひよこ・駒保存則で層別
- **対照A**: 平手からランダムに合法手を指し続けた局面 2,000件
- **対照B**: ランダム配置 2,000件。C++ の生成関数のうち「attacker数>1 の棄却」だけは gamelibs に attacker 数を返す API がなく再現していない。その分は王手特徴量の層別で読み替える

## 結果の読み方（実験5への影響）

| 結果 | 解釈 | 実験5への影響 |
|---|---|---|
| 対照A ≒100%、対照B が低く、違法系特徴で大半を説明できる | DBは正常。未登録はランダム初期局面由来の到達不能・違法局面 | オラクル混合は「DBからサンプルした局面の追加学習」が主軸になる。自己対局局面へのラベル付けは登録済みの約3割にしか使えない。あわせて、ランダム初期局面の生成条件を締める（違法局面の混入を減らす）ことも実験5の候補に入る |
| 対照A ≒100%、対照B も高いのに本体が低い | ランダム配置そのものではなく、自己対局の進行過程で DB 外に出ている | 対局中のどの局面から外れるか（手数・ランダム開始からの距離）を追加調査 |
| 対照A も低い | ハッシュか DB 側の系統的な問題。特徴量の層別でどの局面が落ちるかを見る | オラクル混合の前に照合方法の修正が必須。実験4.5-C/D の数値の解釈も見直しが要る |
| 手番反転キーのヒットが多い | DBのキー正規化の問題 | 照合時に反転キーも引くよう直せば登録率は回復する |

## 注意

- 本体の層別は「登録されている自己対局局面は、到達可能性の点で偏った部分集合」という実験4.5-C の留保を裏付けるためのものでもある。C の lose 崩壊（search 47.1%）が未登録側でも成り立つかは、この調査だけでは分からない
- 対照Bの生成再現は近似。棄却条件の差で対照Bの登録率が本体より多少高く/低く出ても、桁が合っていれば H2 の判定には使える
